# Critic review: Kanvise redesign specs (branch `design/redesign-spec`)

Reviewed: HANDOFF.md, README.md, 00-decisions.md, 01–16 in `/projects/sandbox/kanvise-design/docs/design/redesign/`.
Evidence: Bobbin atlas (`origin/research/bobbin-appatlas`, `scratch/bobbin-appatlas/`), standards 01, 03, 07 and DECISION_LEDGER on `origin/staging`, PlugNMeet reference (`docs/operations/plugnmeet-integration-reference.md`), a code search of `origin/staging` (`api/src`, `web/src`).
Screenshots opened and read: 28 (list in section 3). Extracted to `/projects/sandbox/critic-shots/`.
Note on screenshots: the image viewer returned images unlabelled and not always in request order, so I matched each image to a file name by content and file size. File names in citations are best effort; the quoted text is what I read in the images.
Limits: atlas `screens.json` files hold only generic text ("Captured AppAtlas evidence state"), so Bobbin behaviour was checked from `spec.md` plus the screenshots. I did not open every PNG. Anything I could not confirm is marked *unverifiable*.

## 1. Verdict

**Needs fixes first.** The structure is sound: the Bobbin shell, three-step lesson wizard, join-as-admin pattern, Today / This week / Needs attention dashboard and per-student join links are all copied faithfully. The journey coverage is wide, and the phone work in spec 16 is better than most specs.

But the product cannot be built as written, for six reasons.

1. The specs contradict the owner's own decisions on parents, on "report" versus "Lesson summary", and on the waiting room.
2. The adaptive loop, which is the point of the redesign, has no defined status model. Five features write Knows it / Needs work / Taught / Next with no precedence.
3. Students without an email are cut off from homework, summaries and quizzes, and nothing replaces Bobbin's client-mediated route.
4. Recording is on by default and fed to Kavi, with no consent capture. Bobbin captures consent on the student record, and the Kanvise code has none.
5. Several features are promised that PlugNMeet or the data model cannot deliver as written, or that need approved standards and ledger entries (DOM-010, DOM-009, standards 03 and 07) to be amended first.
6. There are duplicate state IDs, a sidebar route (`/recordings`) with no owning spec, and the Calendar spec is only a "summary".

Roughly two days of consistency and decision work would fix most of it.

1. **Write the course-plan status model** (F-04). Then fix the diagnostic's coverage and guessing problem (F-09), because the adaptive loop is the product's reason for being, and five specs write to it with no rules.
